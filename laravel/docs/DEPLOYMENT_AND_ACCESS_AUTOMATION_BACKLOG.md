# Desire House CMS — автоматизация развёртывания и управления доступом

**Статус:** в работе  
**Дата фиксации:** 24 августа 2026  
**Приоритет:** высокий, до первого production-развёртывания

## Цель

Обеспечить воспроизводимое развёртывание Desire House CMS на PostgreSQL без
ручного создания первого пользователя через Tinker. После установки владелец
должен безопасно создать первого администратора через одноразовый web-мастер,
а затем управлять пользователями, ролями и правами из Filament.

## Зафиксированные проблемы

- `.env.example` исходно ориентирован на SQLite, хотя проект использует
  PostgreSQL и PostgreSQL-специфичный тип `jsonb`.
- База данных и миграции не включены в единый сценарий развёртывания.
- Первый пользователь создаётся вручную через Tinker.
- `User::canAccessPanel()` сейчас возвращает `true` для любого пользователя.
- Filament Shield установлен, но `User` не подключает `HasRoles`.
- В панели нет ресурсов для управления пользователями и ролями.
- Начальная страница сайта не существует до создания контента в CMS; это
  допустимое продуктовое состояние, но оно требует понятного onboarding.

## Архитектурное решение

Создание самой PostgreSQL-базы выполняется инфраструктурным deploy-скриптом с
учётными данными, имеющими право `CREATE DATABASE`. Web-приложение не получает
такие повышенные права. Laravel отвечает за проверку соединения, миграции и
первоначальную настройку данных внутри уже созданной базы.

Web-мастер доступен только когда одновременно выполняются условия:

1. приложение явно переведено в режим установки;
2. соединение с PostgreSQL установлено и миграции завершены;
3. в таблице `users` нет пользователей;
4. предъявлен одноразовый установочный токен из серверного окружения.

После создания первого администратора мастер необратимо закрывается для
обычных web-запросов. Повторный запуск возможен только через серверную CLI-команду.

## Backlog

### DEPLOY-01 — профиль окружения PostgreSQL

**Статус на 25 августа 2026:** PostgreSQL-профиль `.env.example` и пошаговая
инструкция `docs/DEPLOYMENT_GUIDE.md` подготовлены. Автоматический preflight
драйвера и соединения остаётся отдельной задачей.

- Сделать PostgreSQL соединением по умолчанию в `.env.example`.
- Документировать `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`,
  `DB_PASSWORD`, `DB_SSLMODE`.
- Добавить preflight-проверку расширения `pdo_pgsql` и соединения.
- Не хранить production-реквизиты в Git.

**Критерий приёмки:** новый экземпляр приложения получает понятную диагностику
при отсутствии драйвера или недоступности PostgreSQL.

### DEPLOY-02 — создание базы и автоматические миграции

- Подготовить идемпотентный deploy-скрипт для создания пользователя и базы
  PostgreSQL, если они отсутствуют.
- Разделить привилегии provisioning-пользователя и пользователя приложения.
- Выполнять `php artisan migrate --force` при deployment.
- Защитить параллельный запуск блокировкой и журналировать результат.
- Добавить команды проверки `/up` и статуса миграций.

**Критерий приёмки:** повторный запуск не удаляет данные и не создаёт дубликаты;
все миграции применяются автоматически.

### SETUP-01 — одноразовый мастер первоначальной настройки

**Статус на 24 августа 2026:** реализовано базовое безопасное ядро.
Корневой URL перенаправляет в мастер, пока роль `super_admin` никому не
назначена. После назначения роли повторные GET/POST-запросы к `/setup`
перенаправляются на `/admin`.
Команда `php artisan setup:token` автоматизирует включение режима, генерацию и
запись токена; `--no-write` поддерживает окружения с внешним управлением secret.

- Добавить маршрут и приветственный экран установки вне `/admin`.
- Экран показывает состояние PHP, PostgreSQL, миграций и файлового хранилища.
- Кнопка «Создать администратора» доступна только после успешного preflight.
- Запрос защищён CSRF, rate limit и одноразовым `INSTALL_TOKEN`.
- Установочный режим по умолчанию выключен.

**Критерий приёмки:** после появления первого пользователя маршрут возвращает
`404` независимо от знания прежнего токена.

### SETUP-02 — безопасное создание первого super-admin

**Статус на 24 августа 2026:** создание, транзакционная блокировка, одноразовый
показ пароля и роль `super_admin` реализованы. 25 августа 2026 года добавлена
обязательная смена временного пароля: middleware блокирует Filament до успешной
проверки текущего пароля и установки нового пароля по политике сложности.

- Создавать пользователя и назначать роль `super_admin` в одной транзакции.
- Запрашивать имя и логин/email владельца; пароль генерировать криптографически.
- Показывать пароль только один раз после успешной записи.
- Не писать пароль в логи, сессию, URL, аналитику или базу в открытом виде.
- Добавить флаг обязательной смены пароля после первого входа.
- Сделать операцию идемпотентной и защищённой от двух одновременных запросов.

**Критерий приёмки:** в системе может быть создан только один первоначальный
администратор, пароль хранится только как hash, а повторное чтение пароля
невозможно.

### ACCESS-01 — подключение ролей и ограничение Filament

**Статус на 24 августа 2026:** `HasRoles`, permission-миграции, gate-режим
`super_admin` и ролевая проверка `canAccessPanel()` реализованы. Защита
последнего super-admin должна быть выполнена вместе с `UserResource`.

- Подключить `Spatie\\Permission\\Traits\\HasRoles` к `User`.
- Опубликовать и проверить миграции ролей/прав Filament Shield.
- Заменить безусловный `canAccessPanel()` проверкой активного пользователя и
  разрешения на доступ к панели.
- Создать и синхронизировать роль `super_admin`.
- Запретить удаление или понижение последнего активного super-admin.

**Критерий приёмки:** обычный пользователь не может открыть `/admin`, а
super-admin имеет полный доступ.

### ACCESS-02 — управление пользователями в CMS

- Добавить Filament `UserResource`: список, создание, редактирование,
  деактивация и безопасное удаление.
- Добавить назначение ролей и сброс пароля без отображения существующего hash.
- Скрыть системные действия без соответствующих permissions.
- Добавить аудит: кто, когда и кому изменил роль или состояние доступа.

**Критерий приёмки:** super-admin управляет жизненным циклом пользователей из
web-интерфейса без Tinker.

### ACCESS-03 — управление ролями и правами

- Подключить RoleResource Filament Shield или эквивалентный собственный ресурс.
- Сгруппировать permissions по CMS-доменам: контент, медиа, продажи, настройки,
  пользователи и роли.
- Запретить изменение защищённой роли `super_admin` пользователям без
  специального системного разрешения.
- Покрыть матрицу ролей feature-тестами.

**Критерий приёмки:** изменения роли немедленно отражаются на навигации и
доступных действиях Filament.

### ONBOARD-01 — состояние сайта без первой страницы

- Не создавать фиктивную главную страницу без решения владельца.
- Для авторизованного администратора показывать подсказку со ссылкой на
  создание первой страницы.
- Для публичного посетителя возвращать контролируемую заглушку или `404`
  согласно выбранному режиму запуска.
- Добавить checklist первого запуска в Dashboard.

**Критерий приёмки:** пустая CMS не приводит к необъяснимой ошибке `500`.

### NOTIFY-01 — подключаемая доставка учётных данных

- Реализовывать после базового setup-мастера.
- Включать только явной настройкой, например `INSTALL_NOTIFY_ADMIN=true`.
- Отправлять не постоянный пароль, а одноразовую ссылку установки пароля с
  коротким сроком действия.
- Предусмотреть сменные каналы уведомления через Laravel Notifications.

**Критерий приёмки:** при выключенной опции проект не требует настроенной почты;
при включённой пароль не передаётся открытым текстом.

## Рекомендуемый порядок реализации

```text
DEPLOY-01 → DEPLOY-02 → ACCESS-01 → SETUP-01 → SETUP-02
          → ACCESS-02 → ACCESS-03 → ONBOARD-01 → NOTIFY-01
```

## Обязательные проверки безопасности

- два параллельных запроса не создают двух первых администраторов;
- setup недоступен после создания пользователя;
- setup недоступен без install token и при production-конфигурации без явного
  включения;
- пароль отсутствует в логах и HTTP history;
- последний super-admin не может удалить себя или снять с себя критическую роль;
- миграции повторно запускаются без потери данных;
- PostgreSQL используется в интеграционных тестах для поведения `jsonb`.
